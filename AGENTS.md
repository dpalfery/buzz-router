# Instructions for agents working in this repo

## Source of truth

- The active specification is listed in the index declared as **<specification-index>** in the Config Reg below. For v1 that's `buzz-router-v1`.
- Until its `requirements.md`, `design.md` and `tasks.md` are all approved, the folder's `brief.md` is the source of truth. After that, `tasks.md` is the build plan.
- Build exactly what the specification says. If it's ambiguous or wrong, stop and ask David rather than guessing.

## Building

- Follow the build order (brief section 17, later `tasks.md`). Each milestone ends with its tests green on macOS, Linux and Windows CI.
- Keep `crates/router-core` pure: no I/O, no tokio, no clock except the `now` argument. Every routing rule gets a fixture under `fixtures/conformance/` (brief section 15.1).
- The router never calls an LLM.
- Don't modify Buzz. Depend on `buzz-core` and `buzz-sdk` from `https://github.com/block/buzz`, pinned to the `rev` in brief section 2.
- Follow the coding standard declared as **<rust-coding-standard>**. While it's `draft`, treat it as a proposal and ask David before relying on it.
- Never commit keys, nsecs, tokens, real pubkeys or relay URLs. Example config files use placeholders.
- Never run the router against the live relay or real bot keys. Use a local Buzz relay (brief section 15.3).

## Documentation

- The repo is governed by kyber-weave. Every Markdown file under **<docs-root>** carries frontmatter per **<documentation-ontology>**. `component` and `owner` values must exist in **<component-catalog>**.
- Run `kyber-weave docs validate .` before committing documentation changes. CI runs it too.
- Use the `kyber-weave-docs` skill (`.agents/skills/`, `.claude/skills/`) when writing or retrofitting docs.
- One canonical home per fact. Link to the existing document rather than restating it.
- Don't edit between the Config Reg markers below. Change `.kyber-weave/kyber-weave.yml` and re-run `kyber-weave docs init . --no-skill`.
